# D24 — 명시 계약과 테스트 식별

실제 작업일: 2026-11-22 (KST). 날짜 없는 D번호 폴더로 기록합니다.

## 작업과 상태

정확한 JUnit test ID를 명시 계약에 연결합니다. 자동 추정으로 요구사항을 만들지 않습니다.

현재 상태: **구현·로컬 검증**.

관련 파일: `teamsync/requirements.py, docs/phase2/contracts.example.json`.

## 재현·증거

공통 명령: `python -m pytest -q`, `ruff check .`, `npm --prefix web test`, `npm --prefix web run build`. 관련 테스트는 `tests/phase2/`, 브라우저 검증은 `web/e2e/phase2_smoke.py`입니다.

[설계·범위](../docs/phase2/README.md)와 [실행 명령·결과·미검증](../docs/phase2/validation.md)을 확인하세요. 계획상의 완료 기준과 실제 결과를 혼동하지 않습니다. 다음 차수는 자동 진행하지 않습니다.

## 구현 판단과 완료 기준 검토 (2026-11-23)

### 작업

명시 계약을 수집할 형식을 정한다.

### 완료 기준과 실제 달성

완료 기준: 고유 ID·설명·심볼·정확한 test ID가 검증되고 누락은 추정하지 않아야 한다.

실제 상태: 계약 형식 검증. 실제 프로젝트 기본 목록은 비어 있음.

### 구현 방법

Contract와 load_contracts, trusted base의 requirements JSON을 사용한다.

### 대안과 선택 근거

PR 본문에서 자연어 요구사항을 자동 확정하는 대신 유지보수자가 선언한 계약을 택했다. 없는 근거를 생성하지 않기 위해서다. 이는 현재 코드와 기록을 대조한 설계 판단이며, 수행하지 않은 대안 간 성능 비교 실험을 뜻하지 않습니다.

### 개발 중 문제·해결·남은 한계

test ID를 광범위하게 매칭하면 다른 테스트를 근거로 삼을 위험이 있었다. 정확한 ID와 D31 호출 연결까지 확인한다.

증거는 이 README의 관련 파일·검증 기록과 연결합니다. 운영 장애 기록이 없는 설계 위험은 실제 운영 장애로 주장하지 않습니다. 숫자는 각 차수의 실행 기록을 따르며, 이전 통과 수를 현재 코드의 새 실적으로 재사용하지 않습니다.
