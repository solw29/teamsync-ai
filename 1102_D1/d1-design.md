# D1 설계 및 보안 정책

## 개발 전제

- 개발 기간: 1인, 10일, 하루 약 5시간
- 대상: Python 저장소의 PR
- 첫 시연: 비공개 저장소에서 신뢰할 수 있는 팀원만 사용
- 핵심 실행 경로: GitHub Actions + Python 스크립트
- 이번 단계에서 제외: FastAPI, LangGraph, fork PR, Slack, 공개 GitHub App, 일정 조율

## 기능 범위

### 필수

1. PR 생성·갱신 시 `ruff`와 `pytest` 실행
2. 변경 diff와 실행 결과 수집
3. LLM으로 리뷰와 테스트 코드 초안을 JSON 생성
4. 파일·줄 위치 검증을 통과한 리뷰만 게시
5. 생성 테스트를 별도 시크릿 없는 실행 단계에서 제한 시간 내 실행
6. PR당 표시 댓글 하나를 생성하거나 갱신
7. Discord Webhook으로 PR 요약 전송
8. 버그/수정 PR 쌍 평가표 작성

### 선택

- Discord Bot 기반 회의 시간 조율
- 공개 GitHub Action 패키징

## 예상 파이프라인

1. `pull_request`의 `opened`, `synchronize`, `reopened`에서 시작
2. draft PR은 건너뛰고 같은 PR의 이전 실행은 취소
3. 검사 단계에서 `ruff`, `pytest`, diff 수집
4. 분석 단계에서 변경 코드와 검사 요약을 LLM에 전달
5. Pydantic으로 JSON 스키마 검증
6. 파일 및 줄 번호가 실제 변경 diff에 존재하는지 검증
7. 테스트 초안을 임시 위치에 기록해 별도 단계에서 실행
8. 검증 결과를 PR 댓글에 게시/갱신하고 Discord 알림 전송

## 시크릿·권한 정책

- fork PR과 신뢰할 수 없는 기여자는 첫 MVP에서 지원하지 않음
- `pull_request_target`은 사용하지 않음
- 시연 저장소는 비공개로 두고, 팀원만 쓰기 권한을 가짐
- PR 코드 검사·테스트 단계에는 LLM 키와 Discord Webhook을 전달하지 않음
- LLM 키는 분석 단계에서만, Discord Webhook은 게시 단계에서만 사용
- PR 댓글 게시 단계에만 필요한 최소 쓰기 권한 부여
- 생성 테스트 실행 단계에는 시크릿을 전달하지 않고 시간 제한 설정
- PR 코드·주석은 데이터로 취급하며, LLM 출력으로 명령어를 실행하지 않음
- PR에서 workflow 파일을 변경할 때는 검토 전까지 시크릿을 사용하는 흐름을 실행하지 않는 것을 운영 원칙으로 함
- 코드·로그 일부가 외부 LLM API로 전달됨을 저장소 사용자에게 고지

## 댓글 형식

PR마다 고정 마커 `<!-- teamsync-ai -->`가 포함된 댓글 하나를 유지합니다.
재실행 시 해당 댓글을 찾아 갱신합니다.

댓글 섹션:

- 검사 결과: ruff / pytest
- 변경 요약
- 검증된 리뷰 제안 (파일:줄, 근거, 제안)
- 테스트 코드 초안 및 실행 상태
- 분석 실패 또는 diff 생략 여부
- Discord 알림 전송 결과

## MVP 평가 기준

- 버그 PR 중 사전 정의한 버그를 지적한 비율
- 수정 PR에서의 오탐 건수
- 게시 리뷰의 파일·줄 위치가 diff에 존재하는 비율
- 테스트 초안 실행 가능률
- 버그 코드 실패/수정 코드 통과 비율
- PR 시작부터 최종 댓글까지의 실측 시간

테스트 결과 조합은 버그 코드와 수정 코드의 통과/실패 네 경우를 모두 기록합니다.
